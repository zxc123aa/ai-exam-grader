# 决策记录

本文档记录已经明确的产品和技术决策。每条决策后续如有调整，应新增记录，不直接覆盖历史背景。

## D-001 第一阶段优先 Web 系统

- 日期：2026-06-30
- 状态：Accepted
- 决策：MVP 先开发 Web 系统，移动端 App 放到 Web MVP 试点后。
- 原因：教师主要在电脑端完成模板修正、复核、批注和导出；Web 更适合复杂编辑工作流。

## D-002 采用模板驱动流程

- 日期：2026-06-30
- 状态：Accepted
- 决策：系统先建立试卷模板，再基于模板处理学生答卷；不在 MVP 中支持无模板整卷盲识别。
- 原因：模板能稳定记录题目位置、答案区域、分值、题型和评分点，降低识别不确定性。

## D-003 AI 结果必须可解释、可修改、可追溯

- 日期：2026-06-30
- 状态：Accepted
- 决策：AI 模板、OCR、评分和评语均作为建议，教师保留最终确认权。
- 原因：批改结果影响成绩，需要保留原始输入、模型输出、置信度、教师修改和最终结果。

## D-004 分层使用规则、OCR 和视觉大模型

- 日期：2026-06-30
- 状态：Accepted
- 决策：页面处理、配准、客观题和分值计算优先使用规则、OpenCV 和 OCR；视觉大模型主要用于复杂版面、手写答案、主观题和低置信度复核。
- 原因：降低成本，提高可控性，避免大模型承担不适合的确定性任务。

## D-007 复用 OCR 服务承载 Paddle 文档预处理

- 日期：2026-07-03
- 状态：Accepted
- 决策：扫描 V2 的 Paddle 文档预处理能力先复用现有 `ocr-service` GPU 容器，通过 `POST /preprocess` 暴露；不要新建独立 `scan-service` 镜像重复安装 Paddle/PaddleX。`SCAN_ENGINE=scan_http` 默认指向 `http://ocr-service:8010/preprocess`。
- 原因：本机 Docker 在 Windows Docker Desktop 中运行，现有 `ocr-service` 镜像已经安装并验证 `paddlepaddle-gpu==3.3.0` cu130 和 PaddleOCR；重复构建独立扫描镜像会再次下载约 10GB 级依赖，浪费时间和磁盘。实机验证表明 Paddle DocPreprocessor 是单图方向/几何矫正模块，不是横向双页拆分器，因此它应作为“每页矫正”模块使用；横向双页仍需要先做页面检测/拆页，后续优先走页面 polygon 分割模型。

## D-008 题目分割从版面投影转向 OCR anchor

- 日期：2026-07-05
- 状态：Accepted
- 决策：`layout_projection_v0` 仅保留为候选草稿 fallback，不作为准确题目分割方案继续堆参数补丁。下一版题目候选分割优先走 OCR layout + 题号 anchor；若真实样本仍不稳，再进入页面区域分割模型路线。
- 原因：`docs/question-segmentation-evaluation.md` 对 7 个英语/物理真实单页样本评估结果为 `0 pass / 1 review / 6 fail`，主要失败是 `dominant_whole_page_candidate` 整页误框。版面投影和连通区域合并缺少题号、栏边界和语义约束，无法可靠判断题目边界。`layout_ocr_anchor_v1` 第一版已把评估改善到 `3 pass / 3 review / 1 fail`，但仍需处理无题号答题区和过切。

- 日期：2026-07-14

## D-015 多区域题目只生成一个批改项

- 日期：2026-07-14
- 状态：Accepted
- 决策：批改以 `ExamQuestion` 为单位，以首个区域作为兼容主区域键，其余区域按顺序一并交给视觉模型；同一道题不能按区域重复计分。
- 原因：跨页、续块和图文分离题目属于同一评分对象，逐区域判分会造成重复得分和上下文缺失。

## D-016 手机文档扫描采用混合工业级流水线

- 日期：2026-07-15
- 状态：Accepted
- 决策：图片上传默认执行 `hybrid_v2`。先用 OpenCV 检测页面并对每页独立做 Homography；当边界是整图、中心回退或左右页回退时，用 Gemini 3.5 Flash 返回一页/两页 polygon，并通过覆盖率、凸性、页中心间距和重叠率质量门控，失败时允许一次带校验原因的反馈重试；随后对每页调用 Paddle DocPreprocessor 完成方向校正与 UVDoc 展开，若宽高比或清晰度明显退化则保留 Homography 结果。原图永不覆盖，低置信度结果进入人工复核。
- 原因：单纯旋转、投影切分或整图 UVDoc 都无法同时覆盖斜拍、双页、中缝阴影、卷曲和模型偶发错误。混合流水线让确定性几何、视觉边界理解和学习式展开各自只处理擅长的阶段，并通过可回退质量门控避免静默裁题。

## D-017 OCR 证据不一致时保留首轮结果并降置信度

- 日期：2026-07-15
- 状态：Accepted
- 决策：参考算法的宽视图/聚焦视图核验失败或不一致时，不再把首轮并发 OCR 的考生作答清空；保留原始转写，置信度上限降至 0.6，并进入教师复核。作图题在首轮 OCR 后允许追加 Gemini 整块视觉描述，但不得据此自动跳过复核。
- 原因：真实物理卷验证表明，严格一致性门禁会把第 18、20、21、22 题已有的可用转写全部置空，使新流程比原始 GUI 退化。保留低置信度证据既能避免把考生错误“纠正”为标准答案，也能让教师看到原文并有依据地复核。

## D-018 网络核验失败与内容冲突分开校准

- 日期：2026-07-15
- 状态：Accepted
- 决策：宽视图/聚焦视图使用完整规范化转写和数字多重集兼容性判断，不再只比较最后一行。格式、换行、裁边和多带草稿数字不作为冲突；双方数字证据不兼容时仍将置信度上限设为 0.6。`fetch failed` 等核验服务故障保留首轮 OCR 置信度，最高轻降至 0.85，不得伪装成内容冲突。
- 原因：批次 `ce89cbd7-e69b-4949-8878-0787b2df2a7d` 的 66% 是校准策略失真，不是转写准确率仅 66%。修复后同一真实答卷复跑为 84%，仅保留第 20 题真实涂改分歧为 60%。

## D-019 印刷题干标记与学生答案分层

- 日期：2026-07-16
- 状态：Accepted
- 决策：考生对印刷题干的圈出、划线和涂抹不得进入 `studentAnswer`，改为独立的 `printed_question_marks` 证据。实际填入空格的选填词、A/B/C/D 选项字母、计算过程和对印刷文字的显式改写仍保留在作答证据中。主站识别预览必须展示被分离的题干标记，但标明“不参与判分”。
- 原因：第 19 题的“阻力对”是被考生圈出的印刷题干，宽视图和聚焦视图可能稳定地同时识别它，因此“双视图一致”仍不等于“属于答案”。必须再用题干文本、选填候选项和答题槽语义做反污染校验。

## D-020 判分只消费已归属答题槽

- 日期：2026-07-16
- 状态：Accepted
- 决策：识别结果根据印刷小问标号和填空数生成 `answer_entries`，每项包含小问、答题槽序号、文本、状态、置信度和证据坐标。无法稳定归属的内容进入 `unassigned_evidence`，不直接参与判分。Node 生成 `gradingAnswer`，后端规则和 GPT 判分优先且严格使用该字段；字段存在但为空时不得回退到未分层全文。
- 安全门：置信度低于 0.8、双视图证据分歧、核验失败、存在缺失答题槽或无法辨认时，`grading_eligible=false`。后端必须跳过规则/GPT 自动判分，不生成建议分，不改写教师已有分数，直接进入人工复核并写入 `auto_blocked` 审计事件。
- 坐标精度：当前只有题内手写区联集，统一标记为 `answer_region_union`；不宣称是逐字或逐行坐标。后续通过行级检测提升坐标精度。
- 原因：仅有 `studentAnswer` 全文无法表达文字属于哪一小问，也无法阻止题干批注、草稿和边缘噪声进入后续评分。

## D-021 识别效果汇报必须包含文字准确率

- 日期：2026-07-18
- 状态：Accepted
- 决策：任何题目识别、OCR、版面算法或模型对比汇报，必须同时报告文字准确率；平均置信度只能作为模型自评参考，不能替代准确率。
- 口径：有人工确认金标时，默认报告字符级准确率 `1 - edit_distance / gold_chars`，并分开列出题干文字准确率、学生答案文字准确率和综合文字准确率；同时报告 ≥95% 通过题数。
- 无金标时：必须明确写“文字准确率无法计算”，并说明缺少人工确认金标或缺少可对齐预测结果，不能只展示截图、置信度或通过率。
- 原因：历史调试中多次出现“平均置信度 90%”但文字内容错误、模型脑补或框选不完整的问题。验收必须以可对照文本准确率为核心指标。

## D-022 计费分成答卷额度与 Token 积分双轨

- 日期：2026-08-07
- 状态：Accepted
- 决策：面向学校售卖和结算的唯一单位是「答卷份数」（`AnswerQuotaGrant` 等表 + `BillableAnswerSheet` 按 `(org_id, exam_id, billing_identity)` 唯一保证同一份答卷只计一次费）。Token 积分（microcredits）只作为平台内部的上游成本护栏与用量计量，不是第二个客户钱包：学校买足答卷额度后，不得因内部积分为 0 而被拒绝服务。两条轨道分别由 `BILLING_ENFORCEMENT_ENABLED` 和 `TOKEN_BUDGET_ENFORCEMENT_ENABLED` 控制。
- 原因：老师能理解「还剩多少份答卷」，无法理解 token；但平台必须能按模型真实用量核算成本、发现负毛利订单并对账上游渠道。把两者混成一个余额会同时破坏商业可解释性和成本可控性。

## D-023 模型供应链对学校不可见

- 日期：2026-08-07
- 状态：Accepted
- 决策：学校只能从 `PlatformModelOffering` 公开目录中按用途（vision / reference_answer / grading）选择方案，接口只返回展示名、用途和说明。真实渠道、上游模型名、上游成本和路由权重只存在于平台控制面（`ProviderChannel`、`ProviderModelMapping`、`ModelRouteVersion`）。offering 发布前必须校验渠道映射、结构化输出能力和对应用途的路由版本已发布。
- 原因：与 `AGENTS.md` 的产品原则一致——模型名、服务商、并发数不得出现在普通老师界面。同时保留平台随时切换渠道、灰度和熔断的自由度，且不让客户界面成为供应链信息泄露面。

## D-024 成绩以不可变快照发布

- 日期：2026-08-07
- 状态：Accepted
- 决策：学生看到的成绩来自 `ScoreRelease`/`ScoreReleaseItem` 版本化快照，不是实时批注。发布要求无待复核题、每份答卷已评题数不少于已确认题数，且在考试行加锁下串行执行；重新发布生成新版本并把旧版本置 `superseded`。
- 原因：批注在复核过程中会持续变化，学生端若直读实时数据会看到中间态和反复变动的分数。快照同时提供了「成绩以哪一版为准」的审计依据。

## D-026 学生端做零录入的终身错题本，不做拍照搜题

- 日期：2026-08-13
- 状态：Proposed（待确认）
- 决策：学生端的核心不是工具箱，而是「考完试成绩一发布，错题本自己长出来」的零录入积累。明确不提供拍照搜题、不把通用 AI 答疑作为首页、不做题库售卖、不以学生手工录题为主路径。
- 原因：差异化来自数据来源而非功能数量——教师已批改的、带评分点和标准答案的、连续多年的真实考试逐题结果，是消费级学习 App 拿不到的。另一方面，2021 年《关于进一步减轻义务教育阶段学生作业负担和校外培训负担的意见》第 15 条明确线上培训机构不得提供和传播「拍照搜题」等惰化学生思维能力的不良学习方法，教育部随后要求相关作业 App 下线整改并重新审核备案；照搬该功能既有政策风险，也与「教师权威判分」的定位冲突。
- 方案文档：`docs/student-wrongbook-plan.md`。

## D-027 错题本是独立留存的快照，不是教师端数据的视图

- 日期：2026-08-13
- 状态：Proposed（待确认）
- 决策：成绩发布时把错题快照进学习者自己的表，题干、标准答案、评分点、学生作答、失分原因标签、教师评语和裁切图各留一份，只对来源保留 `ON DELETE SET NULL` 弱引用；裁切图复制到学习者命名空间，不依赖考试与答卷。学习者身份与学校租户解耦，错题本读取不受学校服务状态影响。
- 原因：`Exam` 删除会级联清空 documents / regions / submissions / questions / annotations / score releases，裁切图还依赖 `ProcessingTask.output_ref` 或按 `ExamRegion` 实时重裁；`get_current_user` 对每个请求执行 `assert_organization_access`，学校冻结后学生一律 403；`Student` 是班级内实体且不支持改班，升班等于新建档案。这三条意味着「视图式」错题本会在老师删考试、学校欠费或学生升班时静默失效，「伴随一生」无法成立。

## D-028 学生端以微信小程序为主，Web 端保留

- 日期：2026-08-13
- 状态：Accepted
- 决策：学生端优先做微信小程序，Web 学生端继续保留（用于打印、家长在电脑上查看，以及不便安装的场景）。`plan.md` §15 的 React Native App 继续后置。
- 原因：获客靠老师在班级群转发，小程序不用下载安装；家长愿意打开的是微信里的东西；错题本的使用形态是轻量查阅加考前打印，不需要 App 级能力。Web 端复用同一套 API，边际成本低，因此不砍。
- 影响：视觉规范以 `AGENTS.md` 的小程序色板为准；接口设计要同时服务小程序与 Web，不能依赖浏览器专有能力。

## D-029 学生身份走 C 端账号，与学校租户解耦

- 日期：2026-08-13
- 状态：Accepted
- 决策：学生身份以学生自己的账号为锚点，数据跟人走，不随学校合同存续。学校侧的 `Student` 档案降级为「在校经历」，通过 `LearnerEnrollment` 关联到终身的 `LearnerProfile`。学校冻结、升班、转学、毕业都不影响学生访问自己的学习记录。
- 原因：这是「伴随一生的错题本」能否成立的前提。此前 `get_current_user` 对每个请求执行 `assert_organization_access`，学校欠费冻结后学生一律 403；`Student` 又是班级内实体且不支持改班，升班等于新建档案、历史断裂。C 端账号同时也是商业护城河——学生数据不随学校流失而流失。
- 代价（必须在学生端对外开放前完成，见 AEG-071）：
  - 未成年人个人信息处理需要监护人同意，不满十四周岁需单独同意并制定专门处理规则。
  - 需要独立的隐私政策、数据导出与账号注销能力。
  - 需要区分两类数据：学校的教学记录（成绩原件，学校留存）与学生的个人错题本（学生可删）。
  - 微信小程序需要主体资质与合适的服务类目；面向中小学生的移动应用可能需要教育移动互联网应用程序备案。
- 过渡策略：学校仍然可以批量建档并绑定账号（现有流程不变）；学生用自己的账号首次访问时自动生成终身身份，并认领此前挂在其学校档案上的历史错题。等微信登录接入后，学生可把身份换绑到微信，从此脱离学校创建的账号。

## D-025 CI 门禁范围先覆盖可稳定通过的检查

- 日期：2026-08-13
- 状态：Accepted
- 决策：CI 门禁 = 后端 `ruff check` + `ruff format --check`（范围 `backend/app` 与 `backend/tests`）、后端 pytest（真实 PostgreSQL + Redis service 容器，先 `alembic upgrade head`）、OpenAPI 路径冒烟、前端 `biome ci` + `tsc` + `vite build`、以及用 zizmor 审计 workflow 自身。mypy 与 ty 暂不纳入；`backend/scripts` 与根 `scripts/` 不纳入 lint 门禁。
- 原因：mypy strict 与 ty 在当前代码上分别有 588 和 489 条告警，绝大多数是 SQLModel/SQLAlchemy 表达式误报，纳入门禁只会让 CI 长期红灯而失去意义（清理见 AEG-060）。运维与评测脚本按设计使用 `print`，与 T201 规则冲突。E2E 中的 live 用例依赖真实模型 Key 和本机 Chromium，同样不适合作为阻断门禁（分层方案见 AEG-061）。宁可先有一条一定会红/绿的窄门禁，也不要一条永远红的宽门禁。
